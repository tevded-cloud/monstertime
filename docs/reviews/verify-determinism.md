# verify:determinism

Review complete. Findings ranked most severe first.

## Findings

**1. SEVERE, cross-file contract: renaming the creature overwrites every member's personal name, and the wrong names then get written into the permanent action log.**
`D:\Programs\monstertime\src\net\connection.ts` lines 148-155 and 244-255, against `D:\Programs\monstertime\worker\monstertime.ts` lines 538-562.
The server's `name`/`named` messages are the *creature's* name (DO `rename()` writes meta `name`, which becomes `GroupSnapshot.name` and is fed to `deriveCreature` as the creature name; the UI wires `NamePlate` on the creature to `group.rename`, App.tsx:68, Stage.tsx:100). But the client treats them as the *person's* name: `rename()` calls `setLocalName(name)` (connection.ts:251), and the `named` broadcast handler calls `setLocalName(message.name)` on **every connected client** (connection.ts:153). `setLocalName` overwrites the stored actor identity (identity.ts:80-84).
Failure scenario: Alice names the creature "Sparky". Every member's localStorage actor name becomes "Sparky". On each person's next page load, `localActor()` returns name "Sparky", the hello registers them as "Sparky", and every subsequent `act()` stamps `actorName: 'Sparky'` into the immutable actions table. Because derivation applies "most recent name wins" (express.ts:704), all of each person's past contributions are retroactively relabeled to the creature's name: the bond list, presence list, and every memory read "Sparky did this" for everyone. The comment at connection.ts:246-250 shows the author believed `name` was the person's name; the worker author implemented it as the creature's. This is the exact "whose trait is this" corruption the design says is the worst bug the app could have, and the corrupted names are permanent log rows.

**2. Off-by-one: Chronicle stamps traits with the time of the action *after* the one that locked them, and the newest trait gets no time at all.**
`D:\Programs\monstertime\src\ui\Chronicle.tsx:68`: `const stamp = actions[trait.atAction]`. `trait.atAction` is the 1-based count (express.ts:683 `count = i + 1`, stored at express.ts:562/586), so the triggering action is `actions[trait.atAction - 1]`.
Failure scenario: a trait locks on action 5. `actions[5]` is the 6th action, so the row shows the 6th action's time; until that 6th action exists, `stamp` is undefined, `at` is 0, and `ago(0)` renders an empty timestamp (Chronicle.tsx:73, 106-107). The derivation's own memories carry the correct `at`, so the trait headline and its memory row underneath disagree about when the same event happened.

**3. The server accepts stage-gated variants at any stage.**
`D:\Programs\monstertime\worker\monstertime.ts:461`: `act()` checks only `variantById(variantId) !== undefined`. `ActionVariant.minStage` (types.ts:58, enforced client-side via `availableVariants` in ActionBar.tsx:90) is never checked server-side, and the DO never derives the creature to know its stage.
Failure scenario: a hand-rolled client sends `{type:'act', variantId:'train.standGround'}` (minStage 2) as the very first action on a fresh egg. It is validated, stored forever, and pushes pressures the design says cannot exist at that stage. Every client still derives identically (no divergence), but the "not offered below this stage" rule is decoration, and the log is permanently polluted.

**4. All three per-person brakes key on a client-chosen actorId, and `hello` can be re-sent at any time to rotate it.**
`D:\Programs\monstertime\worker\monstertime.ts:441-450` (hello overwrites the seat's actorId with no restriction) and 483-507 (cooldown, per-minute, per-hour limits all query `WHERE actorId = ?`).
Failure scenario: one client alternates `hello` (fresh actorId) and `act` on a single socket. Each rotation resets all three brakes; the only remaining bound is the per-connection flood cap (40 messages/10s), so one person can author the entire 5000-action lifetime log in about 42 minutes, as ~2500 fabricated "people". The comment at line 100-103 claims the per-hour cap makes this take "the better part of a week"; it does not. The design accepts that actorId is not an identity claim, but the stated purpose of these brakes (a creature no one person can grow alone) is silently void.

**5. LOW, bounded: the escalation exception can hand a locus to a strictly *worse*-matching allele, not an "equal match" as documented.**
`D:\Programs\monstertime\src\dna\express.ts:575-581`. When the incumbent is still a live candidate, the challenger must already be top-cosine, so escalation only removes the margin, as documented. But when the incumbent fails its own pace gate in `hasEarned` (its axes' load rate decayed below `threshold/expected`, express.ts:212-218), it drops out of `candidates` while `heldScore` is still computed, and a higher-threshold challenger wins with `score > heldScore + 0.22 + earned - 0.45`, i.e. up to 0.23 (0.08 at max tenure) *below* the incumbent's match. Scenario: horn holds `emberCrest` (thr 5); the group's nourish+ferocity rate drifts under 1.0/action by count ~250 so emberCrest fails its pace gate; an earned `duelRack` (thr 200, escalation 0.45) whose direction matches 0.1 worse than the sitting horn takes the locus. Bounded and arguably tolerable, but it contradicts the written contract at express.ts:89-95.

## Assigned area: what was checked and found clean

- **Cross-engine determinism**: no `Math.random`/`Date.now`/locale calls anywhere in `src/dna`; the only transcendentals in the repo are in `src/forge` (rendering, seeded via `seededRandom('forge:'+seed)`, view.ts:368, never feeding trait decisions) and connection retry jitter. The rational-sigmoid claim holds (`softStep`, express.ts:479-483); every trait decision uses only add/mul/div/sqrt, which are correctly rounded and engine-identical.
- **RNG seeding**: `hashSeed` consumes the full 64-char hex string character by character (rng.ts:26-48), no `parseInt` entropy collapse; `rollGenome` consumes the stream in fixed LOCI/catalogue order; every locus has minStage-1 alleles so `early[firstIndex]` cannot be undefined.
- **Tie-breaking**: candidate sort (express.ts:552), credit sort (334), signatureVariant (375), busiestActors (451), bonds construction (745) all sort by explicit id keys; no decision reads Map/object insertion order.
- **Zero state**: all-zero pressures produce all-zero shapes, `cosine` returns 0 on a zero vector (169), `FIRST_LOCK_MIN` keeps loci bare, morphs come out exactly 0.5 with no NaN. `hasEarned` is only reachable at ticks (count ≥ 5), so actionCount 0/1 never hits the pace gate.
- **Stage thresholds**: `stageFor`/`isGrowthTick`/`progressFor` agree at every boundary (ticks at exactly 5, 18, 48, 110, then 150, 190, ...); molt line indexing never goes negative; `STAGE_ACTIONS[minStage]` indexes match the comment's own examples.
- **Escalation + stickiness + history**: the `past` set makes each locus's history monotone; a replaced allele can never return (express.ts:547), the pool is finite, so no oscillation is possible.
- **Worker ordering**: id and `at` are server-authored, `at` is clamped monotone (512), insert precedes broadcast with no await between (523-535), snapshot reads `ORDER BY n`, and the DO's single-task message handling means a socket always receives its snapshot before any action broadcast; the client dedupes by action id and rebuilds `seenActionIds` from each snapshot. The three-brake SQL binds its parameters in the correct positional order (485-490).
